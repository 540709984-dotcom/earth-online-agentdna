# AgentDNA 协议 v0.1

## 目标

让复杂任务在多人或多 Bot 协作时保留一条可检查的链：**目标 → 证据 → 产物 → 独立验证 → 接收 → 受控改进**。

该协议不负责启动代理、隔离权限、运行定时任务或代替业务审批。宿主是否支持并行代理、跨代理消息和工具调用，必须在实际运行记录中确认。

## 三层双循环

| 层 | 保存什么 | 不能做什么 |
|---|---|---|
| 人的目标与判断 | 优先级、授权、接受标准、价值取舍 | 不能把“已下达”当成“已完成” |
| 团队契约与证据 | 规则、TaskPacket、来源、版本、回执、核验报告 | 不能用文件存在代替事实正确 |
| Bot执行与工具 | 检索、生成、计算、草案、代码、工具结果 | 不能自行批准外部操作或升级规则 |

执行循环关闭当次任务；改进循环只处理已验收结果形成的规则变更候选。运行中的回答不能直接修改长期规则。

## 对象与状态

| 对象 | 最小字段 | 产生者 | 使用者 |
|---|---|---|---|
| TaskPacket | `task_id`、`parent_spec`、目标、输入、权限、验收、预算、停止条件 | 协调者 | 所有参与者 |
| EvidencePacket | `source_ref`、摘录/定位、`claim_status`、日期、适用边界 | 研究者 | 构建者与复核者 |
| HandoffReceipt | 版本、发送者、接收者、已知风险、完整性状态 | 发送者/接收者 | 下游负责人 |
| VerificationReport | 检查项、证据、结论、阻断项、当前版本 | 独立复核者 | 人与接收者 |
| ChangeProposal | 规则差异、证据、适用范围、回归计划、审批状态 | 任一角色 | 人类维护者 |

任务状态固定为：

`draft → active → generated → received → verified → accepted → closed`

`blocked`、`rejected`、`expired` 可以从任一尚未关闭状态进入。`received` 只说明接收者拿到正确版本；`verified` 只说明按当前检查清单通过；`accepted` 才表示人或业务接收者同意使用。

## 角色纪律

- 构建者可以解释产物，不能对自己的关键产物做最终验证。
- 研究者不把无来源主张写成事实；找不到原始材料时标记 `unverified`。
- 复核者核对当前版本、来源和验收项；它不应因草案流畅而关闭问题。
- 接收者确认能否实际使用；这一步不能由文件创建者代签。
- 人决定目标、外部写操作、接受与规则升级。

## 证据等级

| 状态 | 含义 | 可否进入最终事实层 |
|---|---|---|
| `verified` | 已回到一手来源或可执行结果，且定位到当前版本 | 可以，仍需注明适用范围 |
| `reported` | 论文作者/厂商/案例报告的结果 | 可以，必须写清报告者和实验口径 |
| `inference` | 基于多条材料的工程推论 | 可以，明确这是推论 |
| `unverified` | 未取得原始依据或来源冲突 | 不可当作事实；保留为待核 |
| `fictional-example` | 教学用合成内容 | 不可当作实测、客户或业务数据 |

## 最小错误处理

1. 发现问题时引用 `task_id`、产物版本和具体位置。
2. 只退回产生问题的最小步骤；不得让所有角色无上限重写。
3. 记录重试次数、成本、结果和仍未解决的风险。
4. 到达任务包的预算、重试或时间上限时转为 `blocked`，请求人判断。
5. 对外发送、发布、付款、删除或生产变更遵从宿主审批与用户授权。

## 规则传承

只有同时满足以下条件的经验才可提交 ChangeProposal：至少一个已验收任务的可定位证据；明确适用范围；可执行的回归或反例检查；不含私人数据、秘密或客户内容。提案不是批准。人批准后，才创建规则新版本并记录回滚点。
